## Context

ADR-008 gave a session the user's ssh-agent and chose full parity on purpose.
It named the alternative and declined it: "a separate cage key added to
`allowed_signers` so agent work is attributable and revocable on its own." That
was the right call for what a session was at the time, which is a person in a
terminal watching an agent work.

PRD-003 changes what a session is. The supervisor starts runs nobody is
watching, and a reviewer role advances `main` without waiting for anyone. Under
ADR-008 those commits verify as the user, and a signature they did not intend
looks exactly like one they did, which ADR-008 already recorded as
irreversible. Agent forwarding is also wider than signing: the socket answers
any request the agent will answer, so an unattended run can push to a remote,
pull a private repository, or ssh out. PRD-003 forbids publication, but a rule
is the wrong mechanism when the credential to break it is sitting in the cage.

The declined alternative becomes the right one at exactly the point where
nobody is watching, and only there. An interactive session still wants parity;
its whole value is that the person who entered it is accountable for what comes
out.

## Decision

A run the supervisor starts holds no forwarded agent and signs with a key that
belongs to its role.

- `nixcage-container enter` gains `--signing-key`, mutually exclusive with
  `--auth-sock`. Passing both is refused rather than resolved, because a silent
  preference would decide the security property by argument order. The CLI's
  interactive path keeps passing `--auth-sock`, so ADR-008 stands unchanged for
  a session a person entered.
- The key is per role. It is generated on first use at `$STATE_DIR/keys/<name>`
  as an unencrypted ed25519 key, mode 0400, owned by the mapped project owner,
  and bound read-only at `/run/nixcage/signing-key`. It is generated by the
  container script rather than by the agent, so its public half is readable
  without reaching into a cage.
- The session's gitconfig sets `user.signingKey = /run/nixcage/signing-key`.
  Per `git-config(5)`, with `gpg.format = ssh` this may be the path to a private
  key, and git signs through `ssh-keygen` with no agent involved.
  `gpg.ssh.defaultKeyCommand` remains for the interactive path.
- `SSH_AUTH_SOCK` is unset and no socket is bound. An unattended run holds no
  credential that reaches any host, so it cannot push, pull a private
  repository, or authenticate anywhere.
- A role commits under its own declared name and email, not the user's. An
  `allowed_signers` entry binds a role key to that role's address, so a role
  signature is attributable to the role rather than being indistinguishable
  from the user's.
- The container script maintains `$STATE_DIR/keys/allowed_signers` from the
  role keys it has generated and binds it in as
  `gpg.ssh.allowedSignersFile`. Revoking a role is deleting its key and its
  line.

## Consequences

Unattended work becomes attributable and revocable on its own terms. The
question "which role produced this commit, and can I stop it producing more"
has an answer that does not require reading a run record.

An unattended run cannot publish, because it holds nothing that would let it.
PRD-003's "no role pushes to a remote" stops being a policy someone enforces
and becomes a property of what is in the cage.

The private key sits at rest inside the cage for the whole run, which is what
ADR-008 declined for the user's key. The trade is different because the key is
different: it appears in no host's `authorized_keys` and its only authority is
to produce a signature. An agent that exfiltrates it costs the user a
revocation line, not access to anything.

Role signatures do not verify as the user. Anything downstream that requires
the user's own signature has to be re-signed by them, which is consistent with
publication already being their act. A repository whose remote enforces signed
pushes by a specific identity will reject role commits until the role key is
registered there, and registering it hands a remote credential to the thing
this decision was written to keep away from one.

Two signing paths now exist and the caller picks. Nothing inside a cage can
make that choice, since no cage has the CLI, but the supervisor's dispatch path
is now security-relevant code rather than convenience code.

Signature verification inside a cage works for role signatures, which ADR-008
left broken for every signature. The user's own key is still absent from the
rendered `allowed_signers` unless they declare it.

## Verification

The assumption the whole decision rests on is that git signs from a key file
with no agent. Checked on git 2.55.0: with `gpg.format = ssh`,
`user.signingKey` set to a private key path, and `SSH_AUTH_SOCK` unset, `git
commit` produced a commit carrying `gpgsig -----BEGIN SSH SIGNATURE-----`, and
`git log --show-signature` against a matching `allowed_signers` reported `Good
"git" signature`.

bats covers the CLI and container seam: the non-interactive path passes
`--signing-key` and never `--auth-sock`, the container refuses both together, a
role's key is created once and reused on the next run, and a session started
this way has no `SSH_AUTH_SOCK` in its environment. The Nix rendering carries
no bats test, per the infrastructure tier.

The decision makes no performance, storage, or capacity claim, so there is no
measurement plan.
